# commit

변경사항을 읽고, 의미 단위로 나누어, 한국어 컨벤션 메시지로 커밋한다. 커밋은 히스토리에 남는 기록이라 나중에 `git log`만 보고 무슨 일이 있었는지 알 수 있어야 한다. 그래서 "무엇을 바꿨나"보다 "왜/무엇을 위해 바꿨나"가 드러나게 쓰고, 서로 무관한 변경은 섞지 않는다.

## 절차

### 1. 변경사항 분석

먼저 저장소 상태를 확인한다.

```bash
git status --short
git diff            # 아직 stage 안 된 변경
git diff --staged   # 이미 stage된 변경
git log --oneline -10   # 이 저장소의 기존 메시지 스타일 참고
```

- git 저장소가 아니면(`fatal: not a git repository`) 커밋할 수 없다고 알리고, `git init` 여부는 사용자에게 묻는다. 임의로 초기화하지 않는다.
- 변경이 없으면 그렇게 말하고 끝낸다.
- untracked 파일은 `git diff`에 나오지 않으므로 `git status`로 목록을 보고 필요하면 내용을 직접 읽는다.
- diff가 너무 크면 `git diff --stat`으로 윤곽을 잡고 파일별로 나눠 읽는다.
- `.env`, 키, 토큰 등 비밀 정보나 `node_modules`, 빌드 산출물이 섞여 있으면 커밋 대상에서 제외하고 사용자에게 알린다. 한 번 커밋되면 되돌리기 어렵기 때문이다.

### 2. 논리적 단위로 분류

변경을 "하나의 이유로 설명되는 묶음"으로 나눈다.

- 기능 추가, 버그 수정, 리팩터링, 설정/문서 변경은 서로 다른 커밋으로 분리한다. 한 커밋은 한 문장으로 요약되어야 한다.
- 같은 목적의 파일들(예: 컴포넌트 + 그 테스트 + 스타일)은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p`는 대화형이라 쓸 수 없으므로, 분리가 꼭 필요한 경우에만 사용자에게 알리고 한 커밋으로 합칠지 묻는다.
- 변경이 작고 단일 목적이면 억지로 쪼개지 않는다.

### 3. 커밋 메시지 작성

형식:

```
<타입>: <요약>

<본문 - 필요할 때만>
```

타입:

| 타입 | 용도 |
|------|------|
| feat | 사용자에게 보이는 기능 추가·변경 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 빌드·설정·의존성·기타 잡무 |

위 네 가지로 애매하면 이 저장소의 기존 로그가 쓰는 타입(docs, style, test 등)을 따른다.

작성 원칙:
- 요약은 한국어, 한 줄, 50자 안팎, 마침표 없이 쓴다. "~추가", "~수정", "~개선"처럼 명사형으로 끝낸다.
- 파일명이 아니라 의도를 쓴다. "App.css 수정"보다 "다크 테마와 입체형 패널 스타일 적용"이 낫다.
- 요약만으로 이유가 전달되지 않을 때만 본문을 붙인다. 빈 줄 뒤에 왜 바꿨는지, 눈여겨볼 점을 몇 줄로 적는다.
- 코드 식별자, 라이브러리명 같은 기술 용어는 원문 그대로 둔다.
- 환경이 커밋 메시지 끝에 붙일 표기(예: Co-Authored-By 줄)를 지정했다면 본문 맨 아래에 그대로 붙인다. 지정이 없으면 만들어 붙이지 않는다.

예시:
- `feat: 프롬프트 입력창에 Ctrl+Enter 제출 단축키 추가`
- `fix: API 키가 없을 때 생성 요청이 두 번 전송되는 문제 수정`
- `refactor: 컴포넌트 생성 훅의 에러 처리 로직 분리`
- `chore: vitest를 4.x로 올리고 jsdom 설정 정리`

### 4. 사용자 승인 후 커밋

커밋하기 전에 반드시 계획을 보여주고 승인을 받는다. 커밋은 되돌릴 수는 있지만 사용자가 원치 않는 묶음·메시지로 쌓이면 히스토리를 정리하는 수고가 생기기 때문이다.

보여줄 내용:

```
커밋 1: feat: ...
  - src/components/A.tsx
  - src/components/A.test.tsx
커밋 2: chore: ...
  - package.json
```

승인 질문은 한 번에 묶어서 한다(커밋마다 따로 묻지 않는다). 사용자가 메시지나 묶음을 고치라고 하면 반영한 뒤 다시 확인한다.

승인되면 커밋 단위마다 해당 파일만 명시적으로 stage하고 커밋한다.

```bash
git add <파일들>
git commit -m "<요약>" -m "<본문>"
```

- `git add -A`나 `git add .`는 분류에서 제외한 파일까지 끌어오므로 쓰지 않고, 파일 경로를 직접 지정한다.
- hook이 실패하면 `--no-verify`로 우회하지 말고 원인을 보고하거나 고친 뒤 새 커밋을 만든다.
- 이미 만든 커밋을 `--amend`로 고치지 않는다. 사용자가 명시적으로 요청할 때만 한다.
- push는 하지 않는다. 요청이 있을 때만 한다.

마지막에 `git log --oneline -n <만든 커밋 수>`로 결과를 확인해 보여주고, 남은 미커밋 변경이 있으면 함께 알린다.

# create-pr

현재 브랜치의 변경을 읽고, 리뷰어가 "무엇을, 왜, 어떻게 확인하나"를 바로 알 수 있는 PR을 만든다. PR 본문은 코드를 열기 전에 리뷰어가 읽는 첫 문서라서, 커밋 목록을 그대로 복사하기보다 변경의 의도와 확인 방법이 드러나야 한다.

PR 생성은 다른 사람에게 알림이 가는 외부 공개 행위다. 그래서 초안을 보여주고 승인을 받은 뒤에만 만든다.

## 절차

### 1. 사전 점검

```bash
git status --short
git branch --show-current
gh repo view --json defaultBranchRef,nameWithOwner --jq '.defaultBranchRef.name + " " + .nameWithOwner'
```

- `gh`가 없거나 로그인이 안 되어 있으면(`gh auth status`) 그 사실을 알리고 멈춘다. 로그인은 사용자가 직접 해야 한다.
- 현재 브랜치가 기본 브랜치(main/master)면 PR을 만들 수 없다. 새 브랜치를 만들지 사용자에게 묻는다. 임의로 만들지 않는다.
- 미커밋 변경이 있으면 알리고, 커밋을 먼저 할지(`/commit`) 그대로 진행할지 묻는다. PR에는 커밋된 내용만 들어가기 때문이다.
- 이미 이 브랜치의 열린 PR이 있는지 확인한다: `gh pr list --head <브랜치> --state open`. 있으면 새로 만들지 않고 그 URL을 알려준다.

### 2. 변경 분석

기본 브랜치를 `<base>`라고 할 때:

```bash
git fetch origin <base>
git log origin/<base>..HEAD --format="%h %s%n%b"
git diff origin/<base>...HEAD --stat
git diff origin/<base>...HEAD
```

- 앞선 커밋이 0개면 PR할 내용이 없다고 알리고 끝낸다.
- diff가 크면 `--stat`으로 윤곽을 잡고 핵심 파일 위주로 읽는다.
- `.env`, 키, 토큰이 diff에 보이면 PR을 만들지 말고 사용자에게 알린다. 공개 저장소라면 한 번 올라간 비밀은 되돌릴 수 없다.
- 관련 이슈 번호가 브랜치명이나 커밋에 있으면(`#12`, `fix-12-...`) 본문에서 `Closes #12`로 연결한다. 확실하지 않으면 넣지 않는다.

### 3. 템플릿 언어 결정

저장소에 `.github/pull_request_template.md`(또는 `.github/PULL_REQUEST_TEMPLATE.md`)가 이미 있으면 그 템플릿의 섹션을 따른다. 팀이 정한 형식이 우선이기 때문이다. 없을 때만 아래 규칙으로 언어를 고른다.

**한국어 저장소 판정** — 다음 신호를 본다.

1. `README.md`의 본문이 주로 한글인가
2. 최근 커밋 제목 10개(`git log --format=%s -10`) 중 절반 이상에 한글이 있는가
3. `AGENTS.md`/`CLAUDE.md` 등 규칙 문서가 한글인가

1번과 2번이 모두 한국어이거나, 셋 중 둘 이상이 한국어이면 한국어 저장소다. 신호가 서로 갈리거나 판단이 애매하면 영문 템플릿을 쓰고, 어느 쪽으로 판단했는지 초안과 함께 한 줄로 알려 사용자가 바꿀 수 있게 한다. 코드 식별자·라이브러리명 같은 기술 용어는 어느 언어든 원문 그대로 둔다.

### 4. 제목과 본문 작성

**제목**: 한 줄, 70자 이내. 저장소 커밋 컨벤션이 있으면(예: `feat: 요약`) 그 형식을 따른다. 커밋이 하나뿐이면 그 제목을 다듬어 쓰고, 여럿이면 전체를 아우르는 한 문장으로 쓴다. 파일명보다 의도를 쓴다.

본문은 `references/pr-template.md`에서 3단계에서 고른 언어의 템플릿을 읽어 그 구조대로 채운다. 작성 원칙(변경 사항은 의미 단위로 묶기, 실행한 검증만 `[x]`, 빈 섹션 삭제, 환경이 지정한 끝 표기)도 그 파일에 있다. 프로젝트에 테스트·린트·빌드 명령이 있는데 실행하지 않았다면, 그 사실을 초안과 함께 알린다.

### 5. 사용자 승인

이 스킬은 `context: fork`로 분리된 컨텍스트에서 돌아가므로 도중에 사용자와 대화를 주고받을 수 없다. 그래서 두 단계로 나눈다. 처음 호출되면 6단계로 가지 않고 아래 초안을 최종 응답으로 출력한 뒤 멈춘다. 사용자가 승인하며 다시 호출하면(인자에 승인 의사나 수정 지시가 담긴다) 수정을 반영해 6단계를 수행한다.

```
base: <base> ← head: <브랜치>
언어: 한국어 | English (판단 근거 한 줄)
제목: ...
본문:
...
```

사용자가 제목·본문·언어를 고치라고 하면 반영한 초안을 다시 보여주고 멈춘다. Draft PR로 올릴지는 따로 묻지 않고, 사용자가 "draft로"라고 했을 때만 `--draft`를 붙인다.

### 6. 푸시와 생성

브랜치가 원격에 없거나 로컬이 앞서 있으면 푸시가 필요하다.

```bash
git rev-parse --abbrev-ref --symbolic-full-name @{u}   # 업스트림 유무
git push -u origin <브랜치>
```

PR 생성은 승인으로 허락됐지만, 푸시는 별도의 외부 행위이므로 푸시가 필요하면 승인 질문에 "푸시도 함께 진행"을 포함해 함께 허락받는다. 강제 푸시(`--force`)는 하지 않는다.

본문에는 줄바꿈과 특수문자가 많아 셸 인용에서 깨지기 쉽다. 임시 파일에 본문을 쓰고 `--body-file`로 넘긴다.

```bash
gh pr create --base <base> --head <브랜치> --title "<제목>" --body-file <본문 파일>
```

생성 후 임시 파일을 지우고, `gh`가 출력한 PR URL을 사용자에게 알려준다. 실패하면 에러 메시지를 그대로 전달하고, 권한 문제처럼 사용자만 해결할 수 있는 것은 방법을 안내한다.

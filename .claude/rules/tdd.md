# TDD Rule

> **경고: 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 마라.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그것이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리)
- **유틸 함수**
- **버그 수정** (재현 테스트를 먼저 작성)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

경계가 모호하면 **TDD를 적용한다.**

## RED-GREEN-REFACTOR

### 1. RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 마라.
- 테스트를 작성하면 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED가 아니다. 고친 뒤 다시 실행하라.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다. 테스트를 고쳐라.

### 2. GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 테스트가 요구하지 않는 기능, 옵션, 추상화를 추가하지 마라.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### 3. REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 모든 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작 추가 금지.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 삭제 강제 규칙

- 테스트 전에 프로덕션 코드를 먼저 작성했다면 **삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 보고, 복사하고, 주석 처리하고, 옆에 두는 모든 행위가 해당된다.
- 테스트 없이 작성한 코드에 사후 테스트를 끼워 맞추지 마라. 구현에 맞춘 테스트는 구현을 검증하지 못한다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 자주 깨진다. 테스트도 단순하니 30초면 쓴다. 단순하다는 판단 자체가 검증되지 않은 가정이다. |
| "나중에 추가하겠다" | 나중은 오지 않는다. 사후 테스트는 구현을 따라 쓰게 되어 버그를 못 잡는다. |
| "시간이 없다" | 테스트 없는 코드는 디버깅 시간으로 더 비싸게 갚는다. 급할수록 RED부터 시작하라. |
| "삭제하면 낭비" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 테스트 주도로 다시 쓰면 더 빠르고 더 작다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트도 필요 없지만, 남길 코드라면 지금 테스트가 필요하다. |
